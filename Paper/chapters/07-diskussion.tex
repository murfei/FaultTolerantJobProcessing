\section{Einschränkungen und Grenzen der Arbeit}
\label{sec:einschraenkungen}
\textbf{Ausschließlich Notizen}\\
Diese Arbeit betrachtet die Fehlertoleranz ab dem Zeitpunkt, zu dem ein Job persistent im Job-Store vorliegt;
die zuverlässige Auftragserzeugung/Client-Kommunikation (z.B. Outbox, Messaging) ist nicht Gegenstand.
"Consumers may crash at any time, so it could happen that a broker delivers a message to a consumer
but the consumer never processes it, or only partially processes it before crashing. In order to
ensure that the message is not lost, message brokers use \textit{acknowledgments}: a client must
explicitly tell the broker when it has finished processing a message so that the broker can remove
it from the queue." \parencite[Kap.11 --> Acknowledgments and redelivery bzw. Message brokers]{kleppmann_designing_2017}

REST hat keinen Puffer und ist synchron --> Client und Server muss während der ganzen Kommunikation laufen, damit
Kommunikation funktioniert. Weitere Nachteile in Referenc: \parencite[Kap.3.2.2]{richardson_microservices_2018}

Kein Fokus auf Kommunikation im allgemeinen, weder wie oben genannt die Erstellung von Jobs, als auch die Benachrichtigung
bei Fertigstellung. Dafür bräuchte es Transaktionales messaging bspw. mittels transactional outbox pattern \parencite[Kap.3.3.7]{richardson_microservices_2018} oder
asynchrones Messaging \parencite[Kap.3.4.2]{richardson_microservices_2018}

Es gibt keine perfekte reliability \parencite[Kap.~1, Abschnitt \glqq Reliability\grqq]{kleppmann_designing_2017}

Load Leveling umgesetzt?

Performance von DB gegenüber Message Queues

Keine Fehlertoleranz in Bezug auf Datenbeständigkeit (z.B. Festplatte des Job-Stores geht kaputt), Naturkatastrophen (Ganzer Standort fällt aus z.B. wegen Überschwemmung) \parencite[Kap.~9]{newman_building_2026}

Es gibt keine Möglichkeit absolute Garantien zu geben, nur viele Möglichkeiten der Risikoreduktion \parencite[Kap.~7 Abschnitt \glqq The Meaning of ACID\grqq --> Ende]{kleppmann_designing_2017}

um performance zu verbessern könnte man verschiedene checkpoints in die verarbeitung einbringen, sodass bei einem Abbrechen einer Task nicht die gesamte Task neu gestartet wird
sondern ab einem bestimmten punkt wieder angefangen wird \parencite[Abschnitt \glqq Reliability considerations\grqq]{microsoft_corporation_hrsg_best_2026}.

vorsicht bei dingen bei denen kein rollback gemacht werden kann: versendet ein worker eine email, stürzt ab und die operation wird wiederholt wird potenziell noch eine
email versendet. das muss gesondert abgefangen werden

Es können Probleme entstehen, wenn zu viele Anfragen rein kommen, die die DB nicht gleichzeitig verarbeiten kann (vgl. Exmaple \parencite{microsoft_corporation_hrsg_queue-based_2026})
Dafür bräuchte es separates Queue-Based Load Leveling für das Messaging an sich, das System konzentriert sich auf Queue-Based Load Leveling bzgl der Jobverarbeitung. Es werden zwar
Clientseitige Retries durchgeführt, das ist aber keine Garantie, dass die Nachricht trotz hoher Last ankommt

bietet sich vor allem an, wenn man sowieso schon eine db nutzt, man braucht keine zusätzliche Infrastuktur (im Vergleich zum Message Broker, der als eigener Server läuft)

Bei sehr großen Systemen kann die Datenbank aufgrund einer hohen Anzahl Zugriffsversuche jedoch zum limitierenden Faktor werden, sodass dedizierte Messaging-Systeme hinsichtlich des
erreichbaren Durchsatzes Vorteile bieten \parencite[Kap.~11, Abschnitt \glqq Rebuilding state after a failure\grqq]{kleppmann_designing_2017}.

vermeidung komplexität verteilter Transaktionen durch Nutzung lokaler ACID-Transaktionen da alles in dersselben Datenbank liegt

Einschränkung \ref{zus:verarbeitungsgarantie} nur bis zu einem bestimmten Grad --> Kein Job kann verloren gehen, aber ein job wird nicht unendlich oft
recovered da sonst Konflikt mit \ref{zus:terminierung}

- viel fine tuning möglich, was zum einen die Konfiguration der Parameter für Retries angeht (backoff factor, initial delay, maxAttempts)
und zum anderen die genaue Klassifikation der Fehler in transient und permanent, hier vor allem nur zu Vorführungszwecken exemplarisch implementiert

Die vorgestellte Architektur garantiert die Konsistenz der Jobverwaltung und der Ergebnispersistenz.
Seiteneffekte innerhalb der eigentlichen Fachlogik liegen dagegen außerhalb des Verantwortungsbereichs des Frameworks.
Soll die Verarbeitung externer Ressourcen ebenfalls fehlertolerant erfolgen, muss die Fachlogik selbst geeignete Mechanismen wie Transaktionen,
Kompensationsoperationen oder idempotente Operationen einsetzen.

bekanntes Zitat von Dijkstra, sinngemäß: \textit{Testen kann die Anwesenheit von Fehlern zeigen, niemals ihre Abwesenheit.} --> Testing liefert hier grundsätzlich nur notwendige, keine hinreichende Evidenz
